# 分层架构与排障方法论

> 本文档回答两个问题：**这套系统每层长什么样、层间边界在哪**；以及当相机"不工作"时，
> **如何从底层（电气）到顶层（ROS 应用）系统地定位问题**——本项目全部故障的定位过程
> 都遵循这条路径，最终沉淀为 [troubleshooting.md](troubleshooting.md) 的 22 个案例。

---

## 1. 全栈分层视图

```
┌─────────────────────────────────────────────────────────────────┐
│ L7 集成层   rviz2 / 下游节点 / 监视窗口 (GTK)                      │
│            话题 /mv_camera/image_raw(bgr8) + camera_info          │
├─────────────────────────────────────────────────────────────────┤
│ L6 ROS 层    sua_aravis_camera 节点                                │
│            · 采集线程: arv_stream_timeout_pop_buffer → 发布        │
│            · 恢复状态机: STREAMING→REOPEN→USB_RECOVER→WAIT_DEVICE  │
│            · 白平衡策略: AutoSel=off + WBOnce（每次 open 重做）     │
│            · NN 去马赛克(BGGR→bgr8)                                │
├─────────────────────────────────────────────────────────────────┤
│ L5 应用服务层 看门狗 camera-watchdog / 压测 camera-soak / 预览      │
│            · 死亡检测(帧停滞/控制引导失败) + 多级恢复梯              │
│            · usbfs 持有者感知（互不干扰）                           │
├─────────────────────────────────────────────────────────────────┤
│ L4 用户态驱动 Aravis 0.8.31 (usbfs / libusb)                       │
│            · GenCP 控制引导 · GenICam XML · buffer 队列            │
│            ⚠ usbfs 权限(udev) / usbfs 独占(单应用) / 设备命名       │
├─────────────────────────────────────────────────────────────────┤
│ L3 内核     xHCI ← DWC3(fc000000/fc400000) ← usbdp PHY(0/1)        │
│            · 枚举/复位/链路管理 · usbfs 设备节点 /dev/bus/usb       │
│            ⚠ SuperSpeed 链路静默死亡（平台缺陷，本项目的核心对象）   │
├─────────────────────────────────────────────────────────────────┤
│ L2 固件/DTB 设备树: regulators(vcc5v0_host/otg) · gpio-leds(VBUS)  │
│            · PixelFormat 寄存器命名 ≠ 物理 CFA（BGGR）              │
├─────────────────────────────────────────────────────────────────┤
│ L1 电气      VBUS 5V 轨(GPIO3_D5 / GPIO4_B1=PB1) · 相机 MCU 上电   │
│            · 断电=唯一确定的"重启相机"手段                          │
└─────────────────────────────────────────────────────────────────┘
```

**设计原则**：下层的问题尽量在下层修复，但**每一层都要给上层留一个可控的手柄**——
- L1 的手柄是 VBUS 开关（DTB 手术后成为标准 LED sysfs）；
- L3 的手柄是 DWC3 unbind/rebind（sysfs 可写）；
- L4/L5 的手柄是 usbfs 持有者检测（/proc/*/fd 扫描）；
- L6 把这些手柄串成恢复状态机，L5 把它做成无人值守服务。

## 2. 排障方法论：从底到顶的五步法

### 第 0 步：先确认"哪一层在说谎"

相机不工作时，先回答：**设备还在总线上吗？**（L1/L3）
`lsusb`、`/sys/bus/usb/devices/*/speed`。在 → 问题在 L3 以上；不在 → L1/L3。

### 第 1 步：电气层（L1/L2）——"能不能让它断电重启"

- 读 DTB：VBUS 由谁供电？（`dtc -I dtb -O dts` 反编译，grep vbus/phy-supply）
- 找使能引脚 → 判断软件可控性（regulator 约束 / gpio 占用情况）；
- 不可控时的替代路径：同一物理引脚换驱动接管（fixed-regulator → gpio-leds）。

**经验**：物理拔插等效于 VBUS 断电。找出"哪些轨能软件断电"是整台设备
可维护性的分水岭——本项目为此做了专门的 DTB 手术（[troubleshooting A2](troubleshooting.md)）。

### 第 2 步：总线层（L3）——"内核看到了什么、什么没看到"

- `lsusb -t`：树拓扑 + 每设备速率（5000M=SS / 480M=HS）；
- `dmesg | grep usb`：枚举序列、复位、断开；**"零错误事件"本身也是证据**
  （A1 缺陷就是靠"死得无声无息"钉死的）；
- `dmesg` 里的 `LPM exit latency is zeroed` / quirks 打印 = 内核已自动规避项的记录。

### 第 3 步：协议层（L4）——"控制通道活不活"

- Aravis 引导（GCP 控制读取）是最廉价的健康探针：`arv-tool control Width`（root，8s 超时）；
- **枚举成功 ≠ 控制通道活着**（A1 的假死形态）；**控制活着 ≠ 流活着**（A3 僵尸流形态）；
  三种状态必须分别验证。

### 第 4 步：用户态（L4/L5）——"权限、独占、命名"

- usbfs 权限：`ls -l /dev/bus/usb/…`（B3：普通用户枚举失败极易误判为死机）；
- usbfs 独占：`/proc/*/fd` 扫描找持有者（谁握着设备节点）；
- 命名陷阱：Aravis 设备名（GenCP DeviceID）≠ USB 产品名（B2）。

### 第 5 步：图像/集成层（L6/L7）——"像素对不对、话题通不通"

- 通道统计：对 raw Bayer 按四相位采样算均值（`wb_probe.c`）——**绿偏/对调用数字说话**；
- CFA 判别的"增益锚点法"：单独拉高 RGain/BGain，看哪个像素相位响应（`cfa_test.c`）；
- ROS 层：`ros2 topic echo --field encoding`、python rclpy 探针（比 CLI hz 可靠）。

### 贯穿原则：锚点实验

当多个变量互相纠缠（如 WBOnce 同时改了增益寄存器和内部 CCM）、或文档/寄存器
命名与物理事实矛盾时，**找一个系统里唯一可信的因果杠杆做受控实验**：
- 判 CFA：寄存器增益是唯一杠杆 → 拉高单通道看哪个相位跳变（B5）；
- 判 WB 作用面：WBOnce 前后采样对比（B4）；
- 判死因：dmesg 的"无事件"排除了所有会报错的路径（A1）。

## 3. 自愈系统设计

### 恢复梯（强→弱）

```
检测: 15s 周期探测
  ├─ 设备在总线? (sysfs VID 扫描)          不在 → 跳到 L4
  └─ Aravis 控制引导 (timeout 8s)          失败 → 判定假死
恢复:
  L1 authorized 翻转        ~6s   （经验：对假死无效，保留作最快试探）
  L2 usbfs RESET (ioctl)    ~7s   （经验：重枚举但控制仍死）
  L3 dwc3 unbind/rebind     ~13s  （重建链路训练；对真死链部分有效）
  L4 VBUS 断电 3s + 回电    ~25s  （等效物理拔插，100% 复活 ← 兜底）
  全败 → 报 PHYSICAL REPLUG，指数退避(1s→30s)后重试
```

### 三套应用的分工与互斥

| 组件 | 职责 | 相机访问 |
|---|---|---|
| `camera-watchdog` | 空闲期死亡检测+恢复梯 | 探测时短暂持有 usbfs（检测到他人持有即让位） |
| `camera-soak` | 连续推流压测 + 帧停滞检出 + 硬复位 | 长期持有（推流） |
| `sua_aravis_camera` 节点 | 生产采集 + 内置同款状态机 | 长期持有（推流） |
| `camera_monitor`（GTK） | 状态/帧率显示 | **只订阅话题，从不碰相机** |

互斥规则：推流类应用同时只跑一个；usb_recover.sh 的持有者保护保证恢复动作
永不误伤正在运行的应用；看门狗对三者自动让位。

### 为什么监视器不直接探测相机

探测（Aravis 引导）要打开 usbfs——监视器若做探测就会与推流应用竞争。
因此监视器全部信息来自**带外数据**：话题时间戳（fps）、sysfs（设备/速率）、
进程表、日志文件。这让它可以 7×24 常驻。

## 4. 关键数据流

**图像流**：sensor Bayer(BGGR, 8bit) → 相机 ISP 增益(WBOnce 锁定) → usbfs bulk 流 →
Aravis buffer 队列 → 节点 NN 去马赛克 → `bgr8` Image → DDS → rviz/下游。

**恢复流**：帧停滞/引导失败（任一组件）→ 杀掉自己持有的 usbfs → 恢复梯
（L1→L4，usb_recover.sh 带持有者保护）→ 重枚举轮询（9~13s）→ 重新 openCamera
（重设曝光 + 重跑 WB 策略）→ 恢复推流。全链路 14~40s。

**状态流**（监视窗口）：topic 到达时间戳 → fps；sysfs speed/busnum → 链路；/proc 扫描 →
节点进程；日志 tail → 恢复事件。
